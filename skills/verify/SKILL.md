# verify

「書いた」と「動く」は別。動いたのを確かめてから完了を報告する。確認の量は変更の大きさに合わせる。迷ったら1段大きいほうにする。

| 大きさ | 例 | やること |
|---|---|---|
| 小 | 文言・色・数行・設定値 | 動かす |
| 中 | 関数の追加・修正、画面1つ | 動かす＋テスト |
| 大 | 複数ファイルの機能、データの形が変わる | 動かす＋テスト＋境界値・エラー時 |

**動かす**: 既存の確認コマンド（package.json の scripts、Makefile、README）を探して使い、lint やテストがあれば実行する。画面は表示して確かめる（Playwright が使えれば webapp-testing の方法でスクリーンショット）。CLI はふつうの入力で1回実行する。失敗したら直して同じ確認をやり直す。2回直しても通らなければ止めて状況を報告する。出力は成功なら要点だけ、失敗なら詳しく読む。長い出力は末尾だけ見る。

**テスト**: プロジェクトの仕組みに合わせる。なければ一番手軽な方法（Python は assert や pytest、JS は node:test）を使い、新しく入れるときは一言断る。ふつう・境界・失敗するはずの入力の3種類を基本にする。失敗したテストを消したり緩めたりして通さない。

**報告**: 最後に次の形で書く。確認できなかったことは隠さず `未確認: 〜（理由）` と書く。
```
確認: <コマンドや操作> → <結果>
テスト: <追加したテストと結果>（小は「なし」）
```
