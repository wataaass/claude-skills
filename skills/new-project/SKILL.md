# new-project

いきなり作ると方針がぶれる。決めることを決め、記録と確認の仕組みを用意してから作る。

**1. 聞き取り**: grilling の進め方で、質問機能を使って最低限これを決める。目的（誰の何を解決するか、就活でどう見せるか）、最初の版の範囲（作る／作らない）、技術と選んだ理由、公開範囲（リポジトリの公開・非公開、デプロイの有無）、AI との分担（本人が決めること・自分で書きたい部分）。決まったら decision-memo で `DECISIONS.md` に残す。

**2. 雛形**: 次の見出しで `README.md` を作り、答えから埋める（不明な項目は「（未定）」とする）。`CLAUDE.md` も作り、`@DECISIONS.md` と確認コマンドの説明を書く。
```markdown
# <名前>
<1〜2文の説明>
## 制作情報
- 制作期間: YYYY-MM-DD 〜 （制作中）
- 使った AI ツール:
- AI の役割と自分の役割:（自分: … / AI: …）
## 使い方
## 使っている技術
## 設計上の判断
（DECISIONS.md の主なものを「何を／なぜ」で要約）
```

**3. 確認の仕組み**: 最初から1コマンドで確認できるようにする。整形・文法チェック（例: ESLint、html-validate、ruff）、テスト（例: node --test、pytest）、まとめて実行するコマンド（例: npm run check）。実行方法は README に書く。以後のコード変更では verify を使う。

**4. 作る**: 小さく作って動かし、少しずつ広げる。デザインは、ゼロから作るなら frontend-design、既存の改修なら design-taste-frontend を目安にする。方針と食い違いそうなら decision-memo に従う。

**5. 完成後**: README の制作期間と設計上の判断を確定させる。ポートフォリオに載せるか聞き、載せるならサイト（wataaass.github.io）のリポジトリで portfolio-add-work を使う。リポジトリがこの環境になければ、材料（名前、制作期間、役割分担、説明、URL）をまとめて渡す。study-log に節目として残すか聞く。
