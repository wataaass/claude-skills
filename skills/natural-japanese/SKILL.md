# natural-japanese

仕事の文書から note・ブログ・エッセイまで、日本語を読みやすく書く。AI臭さの除去は工程に組み込まれている。

**設計思想**: (1) 検出は機械、判断は AI。AI は自分の癖に気づきにくいので、疑いは機械が決定的に検出し、直すかどうかは文脈で判断する。(2) 事後修正より生成時制約。書く前の設計と書くときの制約で発生を防ぐ。工程は 設計 → 執筆 → 検査 → 収束。

## 実行モード

所要時間の目安: クイックは短文で30秒前後、1万字級で3分程度。フルは短文で7分前後、1万字級で15〜20分。フルを始めるときは目安をユーザーに一言伝える。

**クイック（既定）**: サブエージェントを使わずこの場で完結する。追加で読むのは該当 doctype の型1ファイルだけ（文体憲法は §2 の要約で足りる。他の references は lint の finding で判断に迷ったときだけ開く）。設計（§1）は頭の中で済ませる。検査は lint 1回とスケルトン通読。**lint は短文でも省略しない**（禁止語・翻訳調は1文でも検出される。飛ばすと品質保証が成立しない）。新規 finding がなければ収束は1周で切り上げ、最終パスの通読で終える。references を読み込み始めたら、フルの仕事をしている。

**フル**: 「しっかり」「時間をかけていい」と言われたとき、対外・経営向けなど失敗コストが高い文書、1万字超の文書。フルと決めたら小さな文書でも工程を省かない。lint に加えて outline / terms を実行し、§4 の三つのレビュー（構造・読みやすさ・doctype 照合）を並列のサブエージェントで必ず行う。所見の台帳への統合と「直す／残す」の判断は親が行い、執筆は分割しない（濃淡・比喩の一貫・章間の接続は全体を見ないと守れない）。収束は §5 の状態条件まで回す。過剰と感じても勝手に間引かず、クイックへの切り替えを提案する。effort を選べるならフルは high、クイックは low（低 effort はフルの工程を削りやすいと実測されている）。

迷ったらクイックで仕上げ、「フルで磨き直すこともできる」と添える。

## 呼び出し方

- `/natural-japanese [quick|full] <対象>`: 書く・直す（既定）。新規かリライトかは対象から判断する
- `/natural-japanese write [quick|full] <お題や素材>`: 新規作成。§1（読者・主メッセージ・スケルトン・濃淡・素材集め）から全工程で書く。素材が乏しければ §1-4 で集めるか、ユーザーに求める
- `/natural-japanese score [quick|full|exp] <ファイル>`: 診断のみで、書き換えない。自然度スコア（0〜100、高いほど自然）と理由を返す。quick=lint のみ、full=構造・読みやすさレビュー込み、exp=semantic.py 込み（初回約1GB）。**最初に必ず `references/diagnose.md` を読む**（算出式・バンド・出力形式の定義。読まずに lint の転記で返すのは不可）。リライトの提案はよいが、頼まれるまで直さない

指定がなければ上の基準で選ぶ。自然言語でも同じ（「〇〇について書いて」は write、「AIっぽい？」「採点して」は score）。

## 1. 設計

**1-1 読者・目的・文書タイプ**: 誰が読み、読後に何が起きてほしいかを特定する（不明なら聞く）。型を読む: 議事録 `references/doctypes/minutes.md`、調査・分析レポート `report.md`、社内ガイド・マニュアル `guide.md`、リサーチメモ・ディスカッションペーパー・企画書 `memo.md`、スライド構成 `slide.md`。note・ブログ・エッセイなど型にないものは飛ばす。

**1-2 主メッセージとスケルトン**: 本文の前に主メッセージを一文で書く。書けないなら素材不足（→ 1-4）。見出しは「背景」「まとめ」のようなラベルでなく結論を含むメッセージにし、見出しだけで論旨が通ることを確かめてから本文に進む。

**1-3 濃淡設計**: 全節が同じ熱量・厚みだと「整いすぎた不自然さ」になる。重要な節を厚く、軽い節は軽く、意図的にムラをつける（`references/revision-guide.md`「濃淡設計」）。

**1-4 素材集め（任意、新規執筆時）**: 固有名詞・数値・実例が乏しいまま書くと、一般論しか言えず後から直せない。推論と検索の往復、十分の基準、検索できない環境での素材提供依頼は `revision-guide.md`「素材集め」。

**1-5 文体プロファイル（任意）**: `style-profile.md`（プロジェクトルートか指定の場所）があれば読み、視点・語彙・リズムの癖を下敷きにする。「自分の文体を学ばせたい」と求められたときだけ、`assets/style-profile-template.md` に沿って過去の文章3〜5本から特徴を抽出して書き出す（「傾向として」と留保をつける）。ユーザーが具体的な語や組み合わせを「使わない」「不自然」と明示したら、一般規則に広げず、出典と適用範囲を添えて「避ける表現」に記録する。単語全体ではなく、指摘された組み合わせを最小単位にする。

## 2. 執筆

`references/writing-constitution.md` の12箇条を制約に書く。要点: 結論から書き前置きを書かない／見出しはメッセージ／説明は地の文、箇条書きは真に並列な圧縮だけ／専門用語は「機能→名前」の順で文中説明／固有名詞・数値で接地／太字は文中の核1か所／濃淡をつける／同じ鋳型を3回繰り返さない／「〜ではなく」は本当の誤解訂正だけ／限界と推定はラベルで開示／事実と意見を分ける／結びは再統合し、レポートは So What まで。

この段階では禁止語やリズムを気にしすぎず、内容を出し切る。細部は検査で拾う。

## 3. 検査(1): 静的検知

```
uv run scripts/lint.py --json <file>
```

禁止語・翻訳調・否定肯定対比の反復・文長の均質さ・体言止め率・段落頭の接続詞率・語彙多様性・英語統語の疑いを検出する。exit code は件数にかかわらず 0（入力エラーのみ 1）。ジャンルが明確なら `--genre essay|tech|business` で校正済みの閾値に切り替える（差分は `references/genre-notes.md`）。収束ループでは直前の JSON を `--baseline` に渡すと resolved / new / persisting に仕分けられる。`uv` がない環境（Claude.ai など）では `references/manual-checklist.md` で同じ観点を人手でなぞる。

`scripts/semantic.py` は EXPERIMENTAL な意味的検出器（隣接文の類似度の起伏で話題の平板さを測る。torch・sentence-transformers が必要で、初回約1GB）。フル工程で環境が許すときだけ `uv run scripts/semantic.py --json <file>` を回し、findings は台帳に載せる。

## 4. 検査(2): 判断台帳と二つのレビュー

lint の findings は疑いであり、全部直せという指示ではない。ヒットしたカテゴリの節を `references/revision-guide.md` で読み直し、finding ごとに「直した」か「残す（理由）」を台帳に書きながら判断する（形式は同ファイル「判断台帳」）。用語カタログ: 禁止語 `references/forbidden-patterns.md`、翻訳調 `references/translationese.md`。専門用語が初出で説明されているかは `uv run scripts/terms.py <file>` で候補を列挙して確かめる（カタカナ複合語・略語・固有名詞らしき語を、初出行・回数・説明マーカーの有無つきで出す。説明済みかの判断は人と AI が行う）。

**構造レビュー**: lint は文の表層しか見ず、箇条書き主体の議事録・スライドはほぼ素通りするので、ここが主役になる。見出しと各段落の先頭文だけを読む（`uv run scripts/outline.py <file>` で行番号付きで抽出できる）。
1. スケルトンだけで論旨が追えるか
2. 各見出しがメッセージになっているか
3. 同じ鋳型（定義文の型、節の内部構成、書き出しの文型）の反復がないか
4. 濃淡があるか
5. 結びが So What に接続しているか（レポート系）
6. business・tech の解説、ケーススタディ、レポートで、固定質問への主要回答を後半まで待たせていないか。事実説明とは別に、予告・異変・種明かし・回収を何度も追わせていないか

文書タイプが決まっていれば、doctype の「必須要素」と「AIがやりがちな失敗」も照合する。

**読みやすさレビュー**: `uv run scripts/lint.py --reading-load <file>` で読解負荷の高い箇所（一文長・埋もれた列挙・連続漢字・二重否定・「の」連鎖）を指さしできる。これは AI 臭さとは別目的の推敲用で、スコアにも `--baseline` にも入らない。出力は「見ろ」であって「直せ」ではない。語順、読点、一文一義、主述の距離、こそあどの多用、冗長表現は、機械的な閾値化ができないと実証済み。毎周回、`references/readability-principles.md` と `references/readability-antipatterns.md`（悪文27種を読解負荷順に A→J で分類）を見ながら目視で判断する。**カタログは前から当てる**。A（否定の入れ子）、B（係り受けの距離）、C（語と語形の重さ）は一文の中で計算を強いる高負荷層、H・I・J は文書・表記・読者の知識にまたがる層。短さは目的にせず、事実保持と主述・係り受けを確かめた後の同等候補の間でだけ使う。分割や列挙の展開で字数が増えるのは正しい結果で、不合格の理由にしない。

両レビューで見つけた問題も台帳に一行ずつ起こす。段落が一般論だけ（固有名・数値・実例がない）なら素材の問題であることが多い。情報収集に戻るかは `revision-guide.md`「素材不足の分岐」で判断する。

## 5. 収束

「直した」項目を反映して lint を再実行し、新しい finding がないか確かめる。台帳の全 finding が仕分けられ、修正が新たな finding を生まなくなるまで 3〜4 を繰り返す。同じ finding が2周連続で再発したら `revision-guide.md`「発散ガード」。既存文書のリライトで同じ種類の修正（見出しの結論化、箇条書きの地の文化など）を一律に当てると、元の自然な濃淡が消えてかえって AI 臭が増す。価値を足せる箇所だけ直す（同「改稿を一律に適用しない」）。

## 6. 最終パス

lint と台帳の収束は、既知の表層パターンが消えたことしか意味しない。「無菌室のような冷たさ」「ダラダラした引き伸ばし」が残りやすい。フルモード（と重要な文書）では `references/eval-rubric.md` の6軸ルーブリックで評価する。
1. 脱AI臭・文体の自然さ（プレゼン的な数の宣言・共感煽り・翻訳調ダッシュ・決め文がないか）
2. 情報密度・簡潔さ（不要な前置き・講釈・言い換えの水増しを削いだか）
3. 機能性・走査性（欲しい情報に最短で辿り着けるか）
4. 論理の明晰性と納得感（因果が腑に落ち、実測・具体例で接地しているか）
5. 人間味・誠実さ（書き手の実感と問題意識（Why）があるか）
6. 自己証明力（その文書自体がお手本になっているか）

**合格は全軸90点以上かつ総合平均92点以上**。未達ならボトルネックを特定して改稿し、合格まで回す（詳細は `eval-rubric.md` と `revision-guide.md`）。クイックではこの6観点を頭の中で通読点検し、違和感を直して完了とする。

## 7. 後片付け

中間ファイル（台帳、lint の JSON、下書きのバックアップなど）はすべて削除する。残してよいのは完成した文書と、ユーザーが望んだ場合の `style-profile.md` だけ（`revision-guide.md`「作業ファイルの扱い」）。before/after の例は `references/examples.md`。
