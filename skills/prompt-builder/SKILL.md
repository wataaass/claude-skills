# prompt-builder

あいまいな依頼のまま進めると、Claude は気づかないうちに推測で穴を埋めてしまう。足りない情報を聞き出し、1枚のプロンプトにまとめてユーザーに確かめてもらってから実行する。まとめることで、決まったことが会話に散らばらず、思い込みもユーザーの目で見つけられる。

## 1. 使うかを判断する

自動で使う場合は、最初に「進め方を確かめるため、先にいくつか聞きます」と一言伝える。依頼が明確なら、このスキルは使わずにそのまま作業する。

## 2. 分かることは自分で埋める

プロンプトの項目（§4）のうち、依頼文・会話・プロジェクトのファイル（README、CLAUDE.md、DECISIONS.md、関係するコード）から分かるものは自分で埋める。調べれば分かる事実をユーザーに聞かない。

## 3. 足りない分を聞く

依頼の大きさで聞き方を変え、どちらで進めるかを最初に一言伝える。
- **小〜中の依頼**（バグ修正、機能やページの追加など）: 埋まらなかった項目だけを、質問機能（AskUserQuestion）でまとめて聞く。各問に推奨の答えを付け、1回に4問まで、多くても2回で終える
- **決めることが多く、答えで次の問いが変わる依頼**（新しい制作物の設計、学習や作業の計画など）: grilling の進め方で、決めることがなくなるまで聞く

## 4. プロンプトにまとめる

次の形で書く。30行以内を目安に、ユーザーの答えと調べた事実だけを使う。決まっていない項目は「（未定）」と書き、推測で埋めない。

```markdown
## 目的
<何のために、何をするか>
## 完成の条件
<どうなれば終わりか、どう確かめるか>
## 範囲
- やること:
- やらないこと・触らないもの:
## 制約・方針
<技術、期限、守るルール、DECISIONS.md の関係する決定>
## 材料
<参照するファイル、情報、例>
## 出力
<何をどこに作るか、報告の形>
```

## 5. 見せて確認を取る

プロンプトを見せ、続けて**振り返り**を2〜3行で添える。元の依頼に何を書き足したかと、それがなぜ大事か（書かないと何を推測で決めることになったか）を書く。ユーザーが次から自分で書くときの参考になるようにする。

そのうえで、質問機能で「この内容で実行する／直したい点がある」を聞く。直したい点があれば反映し、もう一度見せる。

## 6. 実行する

確認が取れたら、プロンプトを依頼そのものとして作業する。完成の条件で確かめてから報告する（コードの変更なら verify を使う）。作業中にプロンプトの前提が崩れたら（触らないはずのファイルを変える必要が出た、など）、手を止めて相談する。
